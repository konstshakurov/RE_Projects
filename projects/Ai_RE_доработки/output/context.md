# Контекст проекта «Ai_RE_доработки»

Проект Компетенции 3 (прочие задачи, не ИТ-проект по BABOK) — рабочее
пространство для всех дальнейших доработок платформы **AInalyst** и эпика
**RE_Projects**. Здесь ведётся бэклог улучшений самого агента: новые скиллы,
правки существующих скиллов, изменения структуры эпика, автоматизация и т.д.

Два независимых репозитория под аккаунтом `konstshakurov` — **не форки друг
друга и не связаны общей git-историей**, изменения между ними переносятся
вручную (порт конкретных файлов/скиллов), коммиты в каждом репозитории свои:

| Репозиторий | Локальный путь | Назначение |
|---|---|---|
| [RE_Projects](https://github.com/konstshakurov/RE_Projects) | `c:\Dev\GitHub\konstshakurov\RE_Projects\` | Копия открытого агента AInalyst — эпик со структурой `ainalyst/` + `projects/`, несколько проектов одновременно, все MCP подключены сразу (без переключения фаз) |
| [Ai_RE_Project](https://github.com/konstshakurov/Ai_RE_Project) | `c:\Dev\GitHub\konstshakurov\Ai_RE_Project\` | Версия для сотрудников направления (создана по задаче **KON-17**) — плоский агент на один продуктовый проект: `skills/` в корне (не под `ainalyst/`), свой `CLAUDE.md`/`README.md`/`Rules.md`, фазовый переключатель `phase.py` (генерирует `.mcp.json` под конкретную фазу — экономия контекста, так как один пользователь ведёт один проект) |

**Как переносить изменения между репозиториями:** так как это разные
кодовые базы (например, `skills/common.py` в Ai_RE_Project — намного более
развитая версия, 2000+ строк против ~140 в `ainalyst/skills/common.py` этого
эпика), при переносе доработки в Ai_RE_Project всегда:
1. сверить совместимость интерфейса (сигнатуры функций в `skills/common.py`
   могут отличаться — сначала `diff`, не копировать вслепую);
2. адаптировать пути (`ainalyst/skills/<файл>` → `skills/<файл>`, MCP-сервер
   регистрируется в `phase.py` → `BASE_SERVER`/нужная фаза, а не в `.mcp.json`
   напрямую — там он гитигнорится и генерируется командой `python phase.py`);
3. сделать отдельный коммит в `Ai_RE_Project` (общей истории с `RE_Projects`
   нет, `git push`/`cherry-pick` между ними невозможны).

- **Аккаунт:** `konstshakurov` (владелец обоих репозиториев)
- **Ветки RE_Projects:** `main` (основная), рабочие ветки по фичам —
  например `fix/analyst-skills-copyright`, `feat/kon8-analyst-pre-project`

- **Ветка Ai_RE_Project:** `master`.
- **Трекер задач:** Linear, команда **`Konstantin.shakurov`**, префикс тикетов

## 4. Компетенции AInalyst и созданные скиллы

Полное описание — `README_RE.md` (корень эпика) и `ainalyst/CLAUDE.md`.
Разграничение триггеров между компетенциями — `projects/Rules/Rules.md`,
раздел 1.

| Компетенция | Суть | Когда применяется | Скилл |
|---|---|---|---|
| **1. Оценка аналитики** | Оценка трудозатрат/сроков на этап аналитики, контракт на разработку ещё не заключён. 3 вида: продуктовый проект (минимум артефактов), полная аналитика (максимальная детализация), Discovery/пресейл (уровень ТЗ) | «оцени проект», «посчитай нормочасы», «сколько часов на аналитику» | `ainalyst/skills/analyst_estimate/SKILL.md` (использует тарификатор СимбирСофт `EstimateRE.xlsx`; умеет экспорт в `.xlsx`, KON-22) |
| **2. Аналитика по BABOK v3** | Контракт заключён, команда собрана, разработка идёт. Главы 3–7 (планирование, выявление, жизненный цикл требований, стратегический анализ, проектирование требований) | «создай новый проект», «начинаем проект» | `ainalyst/skills/planning_prep/SKILL.md` и далее по главам |
| **2.1. Предпроект** | Контракт заключён только на предпроектный этап (до контракта на полную разработку). Команда: фуллстек-аналитик + архитектор + PM, 2–3 недели. Отвечает на вопрос «КАК разрабатывать» (в отличие от лёгкой Концепции на присейле — «ЧТО делать»). Результат — техническая «Концепция проекта», раздел 11 которой — архитектурная концепция C4 | «начни предпроект», «сделай/проведи предпроект» | `ainalyst/skills/analyst_pre_project/SKILL.md` |
| **3. Прочие задачи** | Не ИТ-проект: управление, направление аналитики, операционные задачи | «создай папку нового проекта» + не-BABOK содержание | конкретные скиллы/MCP по содержанию запроса (этот проект — пример) |

**Дополнительные скиллы вне глав BABOK** (компания-специфичные + внешние,
GetAnalyst), работают в любой фазе без MCP:
- `analyst_estimate` — оценка трудозатрат (см. выше, Компетенция 1)
- `analyst_pre_project` — техконцепция предпроекта (см. выше, Компетенция 2.1)
- `analyst_it_architecture` — архитектура ПО (ARC42/TOGAF/C4): контекстная/
  контейнерная/компонентная диаграммы, модель данных, API-карта, потоки
  данных, security architecture, НФТ-матрица, техстек, ADR. Приоритетно ведёт
  Архитектор проекта (скилл сам уточняет на Фазе 0); работает в Компетенции 2
  (полный пакет) и в Компетенции 2.1 (только раздел 11 — C4)
- `analyst_db_designer_getanalyst` — проектирование/ревью реляционных БД
  (логическая/физическая модель, ER, PostgreSQL DDL, индексы, миграции)
- `analyst_restapi_designer_getanalyst` — постановка задачи на один REST
  API-метод (контракт, валидации, ошибки, алгоритм, НФТ)
- `analyst_uml_sequence_getanalyst` — UML Sequence-диаграммы в PlantUML с
  самопроверкой синтаксиса

**Правила разграничения (Rules.md, раздел 1.1):**
- Слова «оцени/оценка/нормочасы/часы» → всегда Компетенция 1, даже если
  рядом упомянут «новый проект».
- Слово «предпроект» → Компетенция 2.1 (`analyst_pre_project`), если задача
  «начать/сделать/провести»; но «оцени предпроект» — всё ещё Компетенция 1
  (оценка трудозатрат самого предпроекта, не его выполнение).
- «начинаю новый проект» без слова «предпроект», контракт на полную
  разработку → Компетенция 2 (`planning_prep`, Глава 3).

## 5. Правила эпика (краткая выжимка `projects/Rules/Rules.md`)

1. **Создание проекта:** папка в `projects/`, компетенция определяется по
   формулировке запроса **до** создания папки (таблица триггеров — раздел 1
   выше). Имя по умолчанию `new_номер`, для оценок можно `estimate_<имя>`.
   После создания — автоматический `cd` в папку проекта.
2. **Структура:** каждый проект получает `input/` и `output/`.
3. **Данные:** входящие материалы → `input/` (транскрипты, регламенты,
   записи созвонов и т.д.); результаты (концепции, оценки, требования,
   планы) → `output/`. При обновлении концепции — спрашивать «обновить
   существующий или создать новый документ» (новый → `concept_v2.md` и т.д.).
4. **Изоляция контекстов:** проекты не смешиваются между собой.
5. **Инструментарий:** `ainalyst/` — общий для всех проектов `projects/`.
6. **Переключение:** по триггерам «переключи на проект», «смени проект».
7. **OpenSpec:** используется только по явному дополнительному подтверждению
   пользователя — не предлагается и не запускается по умолчанию.

## 6. Технические заметки платформы

- **Управление фазами BABOK** (`ainalyst/phase.py`) — механизм экономии
  контекста для standalone-режима AInalyst (вне эпика). **В эпике
  RE_Projects фазы не переключаются** — здесь подключены все MCP сразу
  (`.mcp.json`, набор `full`, 22 сервера + Confluence), так как эпик ведёт
  несколько проектов одновременно.
- **Пересчёт путей:** сессия Claude Code запущена из корня эпика, а не из
  `ainalyst/` — все относительные пути инструкций AInalyst (`skills/...`,
  `docs/...`, `phase.py`) отсчитываются от `ainalyst/`.
- **Артефакты MCP-инструментов** (граф трассировки, приоритизация, отчёты
  7.1–7.6) сохраняются в `projects/<project_id>/output/{data,reports,specs}/`,
  а не в отдельном каталоге платформы — `project_id` = имя папки проекта.
- **Формат графа требований:** edge list, ключи `requirements` (узлы) и
  `links` (рёбра), тип связи — поле `relation` (не `type`). Типы: `derives`,
  `depends`, `satisfies`, `verifies`, `modifies` (CR → требование).
- **MCP-серверы Компетенции 2** названы по главам, напр. `babok-ch3`,
  `babok-ch4-41`…`babok-ch4-45`, `babok-ch5-51`…`babok-ch5-55`,
  `babok-ch6-61`…`babok-ch6-64`, `babok-ch7-71`…`babok-ch7-76`,
  `babok-confluence`.

## 7. Назначение этого проекта

`Ai_RE_доработки` — постоянное рабочее пространство для развития платформы
AInalyst и эпика RE_Projects: новые скиллы, изменения `CLAUDE.md`/`Rules.md`,
доработки MCP-конфигурации, исправления багов в существующих скиллах,
эксперименты со структурой эпика. Задачи здесь трекаются через Linear
(команда `Konstantin.shakurov`, тикеты `KON-*`) и коммитятся в
`github.com/konstshakurov/RE_Projects` через PR в `main`.

`input/` — сюда складывать вводные для конкретной доработки (например,
черновики новых скиллов, замечания по существующим, экспортированные
тикеты). `output/` — сюда сохранять итоговые документы по доработкам (планы
изменений, ADR по платформе, ревью скиллов и т.п.), если они не являются
прямым изменением кода/скиллов самого `ainalyst/`.
