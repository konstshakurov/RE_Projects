# Отчёт: трассировка GetAnalyst-скиллов → граф 5.1 (KON-24)

Дата: 2026-09-09. Источник задачи: обратная связь Марии Кубениной по итогам
тестирования скиллов (07.09.2026, п.2) — результат GetAnalyst-скиллов может
«уплыть» от бизнес-требований без прослеживаемости на другие скиллы.

## Сравнение артефактов: BABOK-скиллы vs GetAnalyst

| Артефакт | BABOK (MCP, глава/скилл) | GetAnalyst-скилл | Пересечение? |
|---|---|---|---|
| ER-диаграмма / модель данных | `create_erd` (7.1, `requirements_spec`) — MCP есть, авто-регистрация в графе 5.1, участвует в 7.2/7.3/7.4 | `analyst_db_designer_getanalyst` — логическая+физическая модель, DDL, индексы, миграции — MCP не было | **Да, частично** |
| REST API метод (контракт) | Нет ни одного BABOK-скилла/MCP, проектирующего контракт эндпоинта | `analyst_restapi_designer_getanalyst` — MCP не было | Нет — чистое дополнение |
| UML Sequence-диаграмма | 7.1 создаёт только Use Case Diagram и Activity Diagram | `analyst_uml_sequence_getanalyst` — MCP не было | Нет — чистое дополнение |
| Архитектура/viewpoints требований | 7.4 `requirements_architecture` — организует уже созданные требования по точкам зрения | `analyst_it_architecture` — сам разграничен от DB/REST/UML в своём SKILL.md | Нет — разный уровень (организация требований vs проектирование системы) |

## Выводы

1. Реальное пересечение только одно — **ERD / модель данных**. REST API-метод
   и UML Sequence не конкурируют ни с чем в BABOK — вопрос был не «чей скилл
   лучше», а «как их подключить к графу трассировки».
2. По качеству технического результата (ERD) выигрывает **GetAnalyst DB
   Designer** — production DDL, индексы, миграции против концептуального
   списка сущностей в `create_erd`. Но `create_erd` не заменяется: он остаётся
   единственным звеном конвейера 7.1→7.2→7.3→7.4 (авто-регистрация в 5.1,
   viewpoint «Данные и информация», верификация/валидация).
3. Решение — не конкуренция, а достройка: три MCP-инструмента только
   *регистрируют* уже готовый артефакт GetAnalyst-скилла в графе 5.1, не
   участвуя в самом проектировании.
4. Тип связи в графе — переиспользован существующий `satisfies` (компонент
   реализует требование), новый тип связи не заводился, чтобы не менять схему
   графа и её описание в CLAUDE.md.

## Внесённые изменения

### Новые MCP-инструменты (регистрация в графе трассировки 5.1)

| Скилл | Инструмент | Узел (COMP-*) | Связь |
|---|---|---|---|
| `analyst_db_designer_getanalyst` | `register_physical_data_model` | `COMP-DB-*` | `satisfies` → `ERD-XXX`/`FR-XXX` |
| `analyst_restapi_designer_getanalyst` | `register_rest_api_method` | `COMP-API-*` | `satisfies` → `FR-XXX`/`UC-XXX` |
| `analyst_uml_sequence_getanalyst` | `register_sequence_diagram` | `COMP-SEQ-*` | `satisfies` → `UC-XXX` |

Каждый инструмент сохраняет готовый артефакт (описание/DDL/PlantUML) в
`output/specs/` и регистрирует его как узел типа `component` со статусом
`confirmed`; без переданного `source_req_id` узел регистрируется как
orphan-компонент с явным предупреждением. Все три протестированы на
одноразовом тестовом проекте перед коммитом.

(`C:\Dev\GitHub\konstshakurov\Ai_RE_Project\`) оказался сильно устаревшим —
`git merge-base` с `origin/master` не нашёл ни одного общего предка. На

нужна); локальный `master` сброшен на реальный `origin/master`; коммит с
