# Нормочасы аналитики на продуктовом проекте — черновик методологии (шаг 5)

**Статус:** черновик для согласования. После утверждения переносится в
`ainalyst/skills/analyst_estimate/references/normo_hours_pp.md` (шаг 6).

**Основа:** `artifact_inventory.md` (изучение шаблонов), `survey_results_analysis.md`
(40 ответов ИТ-специалистов), `estimation_criteria_pp.md` (критерии Блоков A–C),
базовые ставки для аналогии — `ainalyst/skills/analyst_estimate/references/normo_hours_catalog.md`.

**Решение пользователя:** за основу шкалы часов взята **LLM-экспертная
оценка** (компактнее ставок каталога в среднем на ~40–50%), а не ставки
`normo_hours_catalog.md` напрямую. Ставки каталога сохранены в таблицах
только как справочная колонка для прозрачности и будущей калибровки.

**Чем отличается от полного каталога:** полный каталог рассчитан на
максимально подробную аналитику (25+ позиций, ставки калиброваны компанией
под этот сценарий). Здесь состав артефактов сужен по данным реального
опроса потребителей, детализация — по факту того, что команды **реально
используют**, а часовые ставки — по независимой LLM-экспертизе объёма работы
для лёгкого продуктового/agile-процесса (не унаследованы от «тяжёлой» шкалы
каталога). **Это стартовая, не эмпирическая шкала** — требует калибровки на
первых 2–3 реальных продуктовых проектах (см. открытые вопросы, раздел 5).

---

## 0. Статус шкалы: стартовая, подлежит калибровке

**Зафиксировано в методике:** часовая шкала раздела 3 — **стартовая**, а не
проверенная эмпирически. Она получена LLM-экспертизой (не измерениями на
реальных проектах СимбирСофт) и должна использоваться с этим статусом до
первой калибровки.

**Условие калибровки:** после того как по этой методике будут оценены и
проведены **2–3 реальных продуктовых проекта**, плановые часы по каждому
артефакту сравниваются с фактически потраченными, и ставки раздела 3
корректируются по факту. До калибровки — любая оценка по этой методике
должна сопровождаться пометкой **«оценка по стартовой, не откалиброванной
шкале»** в отчёте BA.

## 1. Правило выбора уровня: детализация → сложность

Опрос описывал детализацию 4 градациями (Не нужен / Краткая / Средняя /
Подробная). Часовая шкала методики (раздел 3) задана по тем же 3 уровням
сложности 1/2/3, что и каталог СимбирСофт — только сама шкала часов
пересчитана по LLM-экспертизе (см. раздел 3.0). Сопоставление детализации и
уровня:

| Детализация (опрос) | Уровень сложности (расчёт часов) |
|---|---|
| Краткая | 1 (простой) |
| Средняя | 2 (средний) |
| Подробная | 3 (сложный) |

**Правило выбора уровня по умолчанию:** берётся мода (самый частый ответ)
опроса. **Экономное правило при близком разрыве:** если мода опережает
следующий по популярности вариант менее чем на 10 п.п. **и** этот сосед —
более дешёвый уровень, по умолчанию берётся более дешёвый (соответствует
главному ограничению проекта — конкурентоспособность КП по стоимости).
Итоговое решение всегда может скорректировать BA — это дефолт, не жёсткое
правило.

**Важно:** это правило про *базовую детализацию текста*, а не про
объективную сложность объекта (число ролей, ветвлений и т.д.) — если сама
система объективно сложнее (см. критерии 1/2/3 в `normo_hours_catalog.md`
для конкретного пункта), финальное решение по уровню — за BA, дефолт из
опроса не должен маскировать реальную сложность.

## 3. Ставки часов по артефактам

### 3.0 Как получена шкала методики

Для каждого артефакта посчитано отношение `LLM-оценка ÷ ставка каталога на
дефолт-уровне из опроса` (см. предыдущую версию черновика — числа сохранены
там же как контрольные точки). Это отношение применено ко **всем трём**
уровням 1/2/3 каталога — так сохраняется прогрессия сложности внутри
артефакта (уровень 3 всегда дороже уровня 1 в той же пропорции, что и в
оригинале), но вся шкала сдвинута вниз до объёма, типичного для лёгкой
продуктовой аналитики. Итоговая ставка каждого артефакта — это шкала
методики на дефолт-уровне из опроса (раздел 1).

### 3.2 Новые позиции — теперь также в `normo_hours_catalog.md`

Раньше в компании такого норматива не было вовсе. По итогам этого проекта
эти 4 позиции **добавлены в основной каталог** `normo_hours_catalog.md` —
пункты 2.8, 2.9, 4.9, 4.10 — с полной (не дисконтированной) шкалой часов,
той же по духу, что и остальные пункты каталога. Для продуктовых проектов
здесь по-прежнему используется LLM-дисконтированная шкала (столбец
«Итоговая ставка»), а колонка «каталог» — новые ставки полной методики,
теперь уже утверждённые, а не гипотетические.

| Артефакт | Ед. измерения | Пункт каталога | Шкала методики (LLM): Ур.1/2/3 (ч.) | Для сравнения: шкала каталога (Ур.1/2/3) | Дефолт-уровень | **Итоговая ставка** |

Статусная модель — единственная из четырёх, где шкала методики и шкала
каталога совпали: она изначально оценивалась «с нуля» под компактный
продуктовый объём, а не по аналогии с более «тяжёлым» пунктом каталога.

**Важно про ТЗ:** «ТЗ» в опросе — не отдельный содержательный артефакт, а
контейнер: часы на его разделы (бизнес-процессы, роли, ФТ, сущности,
интеграции) уже считаются отдельными строками в 3.1. Эта строка — только
компоновка, форматирование и сквозная редактура готового документа.

### 3.3 Руководства — ситуативные, шкала также пересчитана по LLM-экспертизе

Данных опроса по нужности/детализации нет (артефакты выпали из финальной
анкеты, см. `survey_results_analysis.md`). У каталога (5.1) для этих пунктов
только одна фиксированная ставка без деления на уровни — LLM-экспертиза
применена к ней напрямую (типовой коэффициент ~0,5, тот же порядок, что и по
большинству артефактов 3.1):

| Артефакт | Ставка каталога (фикс., для сравнения) | **Итоговая ставка методики** | Включать, если |
|---|---|---|---|
| Руководство пользователя | 36 ч. | **18 ч.** | есть интерфейс конечного пользователя |
| Руководство администратора | 34 ч. | **17 ч.** | есть админ-панель/бэкофис |
| Руководство по развёртыванию | 35 ч. | **18 ч.** | self-hosted / on-prem развёртывание (не нужно для чистого SaaS без доступа клиента к инфраструктуре) |

### 3.4 Исключено по умолчанию

**Конкурентный анализ / SWOT** — 65% «не нужен», 0% «всегда». Не включается
в типовую продуктовую оценку. Это pre-sale-активность, а не задача аналитика
на проекте — включать только по прямому запросу (например, отдельная услуга
«исследование рынка»).

## 4. Иллюстративный пример (не реальная оценка, только для проверки методики)

Гипотетический малый продукт: 8 ФТ-совокупностей, 5 ролей, 3 US, 2 сущности
реляционной БД, 2 REST-интеграции, есть админ-панель, нет брокера сообщений
и NoSQL, ТЗ нужен управленцам (Блок C1 = да → детализация ТЗ на максимум,
уже дефолт).

| Артефакт | Кол-во | Итоговая ставка | Часы |
|---|---|---|---|
| ФТ | 8 | 5 ч. | 40 |
| ТЗ — компоновка | 1 | 8 ч. | 8 |
| REST/SOAP | 2 | 6 ч. | 12 |
| Роли | 5 | 4 ч. | 20 |
| Бизнес-цели | 1 | 2 ч. | 2 |
| User Story | 3 | 1,5 ч. | 4,5 |
| НФТ | 30–40% от ФТ (мин. граница) | 30% × 40 | 12 |
| Сущности / БД | 2 | 2,5 ч. | 5 |
| Руководство администратора | 1 | 17 ч. | 17 |
| **Итого (минимальная оценка, от)** | | | **≈120,5 ч.** |

Для сравнения: тот же состав по прежней шкале (напрямую унаследованной от
каталога) давал 266 ч. — больше в 2+ раза. По полному каталогу СимбирСофт
(уровень 3 везде, все пункты, включая Карту экранов и Прототипы) цифра была
бы ещё выше. Методика продуктового проекта на LLM-шкале компактна за счёт
трёх факторов сразу: (а) более узкий состав артефактов, (б) более низкий
дефолт-уровень детализации, (в) собственная более экономная часовая шкала.

2. ✅ Дефолт-уровни по экономному правилу подтверждены без изменений (Роли,

3. ✅ Ставки новых позиций подтверждены. Дополнительно: Статусная модель,

   для основной методики; в продуктовой методике (этот документ) по-прежнему
   используется LLM-дисконтированная шкала. Ставки Руководств (3.3) тоже
   подтверждены без изменений.
4. ⏸ Перенос в `SKILL.md` (шаг 6) — **на паузе по просьбе пользователя**.

   только затем вернуться к шагу 6.
