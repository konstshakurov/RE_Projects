**Источники:** `input/templates_full/` (9 файлов), `input/templates_pp/` (10 файлов),
сверка с `ainalyst/skills/analyst_estimate/references/normo_hours_catalog.md`.

## Главный вывод

Шаблоны `templates_pp` — это ОРИЕНТИРЫ, а не готовый набор "лайт"-версий:
детализация некоторых из них (Use Case, API методы и контракты, НФТ) не ниже,
а местами выше, чем в аналогах из `templates_full`. **Ни в одном шаблоне нет
встроенной шкалы сложности** — критерии 1/2/3 существуют только в
`normo_hours_catalog.md`. Вывод: уровень детализации для продуктового проекта
нужно задавать методологией/критериями (шаг 4) и подтверждать опросом
(шаг 3), а не выводить автоматически из факта "это шаблон из templates_pp".

## Что это значит для методологии продуктовых проектов

1. Для артефактов, прямо покрытых каталогом (14 из 18) — можно опираться на
   существующие нормочасы, но пересмотреть уровень детализации/сложности под
   продуктовый проект (не переносить автоматически).
2. Для 4 непокрытых позиций нужны новые решения:
   - **Конкурентный анализ + SWOT** — включать в продуктовую методику как
     отдельный пункт (частый артефакт для продукта) с новой нормой часов.
   - **Чек-лист ревью ТЗ (Вигерс)** — процессный инструмент качества, не
     отдельно оцениваемый артефакт-документ; не включать в нормочасы, но
     упомянуть в методологии как обязательную практику.
   - **NoSQL БД** — новый пункт, аналог 4.1, но с учётом вложенных структур/
     JSON Schema.
   - **Статусная модель** — вынести из 4.5 в отдельный пункт с диаграммой.
3. Опрос ИТ-специалистов (шаг 3) должен собрать данные именно о нужности и
   детализации этих артефактов на продуктовых проектах — включая новые виды,
   не имеющие аналога в текущем каталоге.
