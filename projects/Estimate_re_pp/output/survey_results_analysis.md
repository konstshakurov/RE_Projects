## ⚠️ Проблема качества данных — требует решения

При переносе опроса из `survey_it_specialists_v1.md`/`.docx` в Google Forms **3 из
18 запланированных артефактов не попали в финальную анкету**:

- Руководство пользователя
- Руководство администратора
- Руководство по развёртыванию / для системного программиста

В выгрузке это видно по двум полностью пустым столбцам-«призракам»
(`Нужность [Ряд 15]`, `Нужность [Ряд 16]` — 0 заполненных из 40), которые
Google Forms создаёт, когда строка сетки была переименована/удалена ещё до
получения ответов. Судя по всему, эти строки были превращены в **«Конкурентный
анализ / SWOT»** и новый, не запланированный изначально пункт **«Бизнес-цели»**
(эти два пункта в выгрузке заполнены на 100%).

**Решение нужно принять сейчас:**
1. Оценивать эти 3 артефакта (руководства) экспертно/по каталогу
   `normo_hours_catalog.md` без данных опроса, либо
2. Провести короткий точечный до-опрос (mini-poll, 1 вопрос на 3 пункта) по
   этим 3 артефактам отдельно.

## Качественные темы из открытых ответов

**Чего не хватало (в. 39)** — повторяющиеся темы:
- Недостаточно проработаны **corner-cases / альтернативные сценарии** в ТЗ и Use Case (несколько ответов)
- Путаница между **User Story и Use Case** — команда не всегда понимает разницу
- Не хватает **бизнес-контекста**: зачем делается фича, какой бизнес-результат ожидается (перекликается с высоким спросом на «Бизнес-цели» из таблицы выше)
- Детальное описание **структуры БД** (типы данных, связи)
- Мокапы/дизайн, глоссарий, тест-кейсы

**Когда артефакт был избыточным (в. 40)** — повторяющиеся темы:
- «Много воды» — большие Word-документы вместо краткого структурированного текста
- Огромные таблицы параметров для REST API вместо ссылки на Swagger/OpenAPI
- Смешение ответственности fronted/backend в одном артефакте
- Устаревшие данные вперемешку с актуальными (несколько упоминаний — см. ниже)
- Технические детали, мешающие быстро понять бизнес-задачу

**Главный признак качества (в. 41)** — доминирующая тема (упоминается в
абсолютном большинстве ответов, часто первым словом): **актуальность**.
Далее по частоте: непротиворечивость, краткость (но не в ущерб полноте),
наличие примеров, понятная навигация/структура (оглавление, нумерация,
ссылки), явная связь с бизнес-задачей.

**Вывод для методологии:** «актуальность» и «непротиворечивость» — это не
параметры детализации/сложности отдельного артефакта, а требование к
**процессу ведения** документации (обновлять, а не плодить дубликаты). Стоит
зафиксировать как отдельный принцип методологии, не как строку нормочасов.

## Что это значит для шага 4 и шага 5

1. **Явный кандидат на исключение по умолчанию:** Конкурентный анализ / SWOT
   (65% «не нужен», 0% «всегда») — не включать в типовой набор продуктового
   проекта, отметить как pre-sale-артефакт вне зоны аналитика на проекте.
2. **Ядро (высокий приоритет, «Всегда» >60%):** Функциональные требования, ТЗ,
   Интеграция REST/SOAP.
3. **Новый обязательный кандидат:** Бизнес-цели — не было в исходном каталоге
   нормочасов вообще, но респонденты сами про него написали и оценили
   востребованность на уровне User Story/Ролей. Нужно добавить в
   `normo_hours_pp.md` как новый пункт.
4. **Ситуативные артефакты («Иногда» доминирует, включать по критериям
   проекта, не по умолчанию):** Use Case, Статусная модель, NoSQL БД,
   Бизнес-процесс, Асинх. интеграция — это прямой материал для критериев шага 4
   (например: «есть очереди/брокер в архитектуре?» → включать асинх.
   интеграцию; «есть NoSQL в стеке?» → включать NoSQL БД).
5. **Детализация:** нет ни одного артефакта с уверенным консенсусом на
   «Подробная» выше ~57% — то есть дефолтный уровень детализации для
   продуктового проекта должен быть **ниже**, чем в
   `normo_hours_catalog.md` (рассчитанном на максимально подробную аналитику),
   в среднем на уровне «Средняя» с повышением до «Подробная» только для ФТ и
   интеграций.
6. **Открытый вопрос к пользователю (см. предупреждение выше):** как закрыть
   пробел по 3 «Руководствам» — экспертно по каталогу или через до-опрос.
